# AGENTS.md

Guidance for AI agents (and humans) working in this repository. Read this
before touching releases, changelogs, or anything published.

## This is a closed-source product

`strvmarv/zoid` is **private**. Binaries are distributed from the **public**
`strvmarv/zoid-releases` repo. Never leak source, internal architecture, or
implementation detail into anything that reaches the public repo (release
notes, installer scripts, marketing site). When in doubt, treat content as
public-facing and omit specifics.

## Release notes: two audiences, two files

There are **two** changelogs. Do not conflate them.

| File | Audience | Published? | Register |
|------|----------|-----------|----------|
| **`RELEASES.md`** (root) | Customers / beta testers | **Yes** — cargo-dist parses the `## X.Y.Z` section matching the tag and publishes it to `strvmarv/zoid-releases` | Commercial: capabilities and fixes, benefit-oriented. **No** crate names, algorithms, file paths, or internal jargon. |
| **`docs/CHANGELOG.md`** | Developers | No | Detailed engineering record. Free to reference internals. |

Why `docs/CHANGELOG.md` and not root: cargo-dist auto-detects a **root**
`CHANGELOG*`/`RELEASES*` file for release notes. Keeping the dev changelog
under `docs/` ensures dist reads **only** `RELEASES.md` (no ambiguous
precedence between two root files). Do not move the dev changelog back to the
root, and do not add a second root changelog file.

Each `RELEASES.md` version header must be a bare `## X.Y.Z` that matches the
tag (e.g. `## 0.2.0` for tag `v0.2.0`), or dist won't find a section to
publish. Write the narrative only — dist appends the install one-liners and
download table automatically.

## Cutting a release (summary)

Full runbook: **`docs/RELEASING.md`**. In short:

1. Bump `[workspace.package].version` in the root `Cargo.toml` (workspace-
   inherited; `zoid-testkit` is intentionally pinned and excluded).
2. Add a customer-facing `## X.Y.Z` section to **`RELEASES.md`**; add the
   detailed entry to `docs/CHANGELOG.md`.
3. Regenerate the TUI snapshots — the status bar renders the version, so a
   bump changes ~35 insta frame snapshots. Run
   `cargo insta test --accept -p zoid-tui` and confirm `git diff` is
   **version-token-only** before committing them.
4. Verify the release gate: `cargo test --workspace --features zoid/local-embed`
   (dist bakes in `local-embed`). Never trust a piped exit code; use
   `--no-fail-fast` so one failing test binary can't hide others.
5. Commit, then `git tag vX.Y.Z && git push origin main --tags`. The tag push
   fires `release.yml`.

## Do not hand-edit `.github/workflows/release.yml`

It is generated by `dist generate` from `dist-workspace.toml`. Re-run
`dist generate` after any `dist-workspace.toml` change. The customization seam
we own is the custom publish job `.github/workflows/publish-public.yml`, which
runs sandboxed (no checkout of the private repo, `contents: none`) and mirrors
the release to `strvmarv/zoid-releases`.

## Memory

The maintainer (strvmarv) uses the **total-recall** MCP as the system of
record for decisions/corrections/preferences. Persist durable facts there;
do not hand-write into host memory files.
