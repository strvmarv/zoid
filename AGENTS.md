# AGENTS.md

Guidance for AI agents (and humans) working in this repository. Read this
before touching releases or changelogs.

## Release notes

`CHANGELOG.md` (root) is the single changelog — customer-facing and
developer-facing content live together in one file. Each version's `## X.Y.Z`
section must be a bare header matching the tag (e.g. `## 0.2.0` for tag
`v0.2.0`), or cargo-dist won't find a section to publish as that release's
announcement notes. Write the narrative and the engineering detail together;
dist appends the install one-liners and download table automatically.

## Cutting a release (summary)

Full runbook: **`docs/RELEASING.md`**. In short:

1. Bump `[workspace.package].version` in the root `Cargo.toml` (workspace-
   inherited; `zoid-testkit` is intentionally pinned and excluded).
2. Add a `## X.Y.Z` section to the top of **`CHANGELOG.md`**.
3. Regenerate the TUI snapshots — the status bar renders the version, so a
   bump changes ~35 insta frame snapshots. Run
   `cargo insta test --accept -p zoid-tui` and confirm `git diff` is
   **version-token-only** before committing them.
4. Verify the release gate: `cargo nextest run --workspace --features zoid/local-embed --no-fail-fast`
   (dist bakes in `local-embed`). Nextest emits a single reliable exit code
   (no piped-exit-code hazard) and parallelizes at the test level across all
   binaries. Use `--no-fail-fast` so one failing test doesn't hide others.
   `cargo test --workspace --no-fail-fast` still works as a fallback.
5. Commit, then `git tag vX.Y.Z && git push origin main --tags`. The tag push
   fires `release.yml`.

## Do not hand-edit `.github/workflows/release.yml`

It is generated by `dist generate` from `dist-workspace.toml`. Re-run
`dist generate` after any `dist-workspace.toml` change.

## Terminal minimum size

The TUI enforces a hard minimum of **160×40** (`layout::MIN_WIDTH` /
`MIN_HEIGHT`). Below this, a "too small" overlay renders instead of the normal
shell — `render_shell` and its sub-functions (`render_status`, `render_title`,
etc.) never run. This means renderers can assume at least 160 columns: no
narrow-terminal fallback, degradation, or progressive-collapse logic is needed
in render code.

## Memory

The maintainer (strvmarv) uses the **total-recall** MCP as the system of
record for decisions/corrections/preferences. Persist durable facts there;
do not hand-write into host memory files.
