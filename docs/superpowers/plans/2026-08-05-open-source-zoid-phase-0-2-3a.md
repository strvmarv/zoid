# Open-sourcing zoid — Phase 0 + Phase 2 + Phase 3a Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Formalize the dual MIT/Apache-2.0 license across the workspace, remove the closed-source/private-public-mirror machinery from the repo, and author the baseline docs (README, CONTRIBUTING, SECURITY) a public repo needs — all without touching `crates/*` product behavior.

**Architecture:** This is repo/config/docs work, not application code. Each task edits or removes specific files (Cargo manifests, GitHub Actions workflows, `dist-workspace.toml`, root docs) and verifies the outcome with a concrete command (`cargo metadata`, `dist generate`, `grep`, `git status`) rather than a unit test.

**Tech Stack:** Cargo workspace (14 member crates), `cargo-dist` 0.32.0 (`dist` CLI, already installed locally), GitHub Actions.

## Global Constraints

- Do not modify any file under `crates/*/src/` — this plan is repo/process only, per the spec's non-goals.
- License text: dual **MIT OR Apache-2.0** (spec: `docs/superpowers/specs/2026-08-05-open-source-zoid-design.md`, "Locked decisions").
- Do not hand-edit `.github/workflows/release.yml` — it is generated by `dist generate` from `dist-workspace.toml`. Re-run `dist generate` after any `dist-workspace.toml` change, per existing `AGENTS.md` convention.
- This plan does **not** flip repo visibility, touch `strvmarv/zoid-releases`, or post anything publicly — those are Phase 1 (audit) and Phase 3b (flip), which are separate, out of scope here.
- Source of truth for scope: `docs/superpowers/specs/2026-08-05-open-source-zoid-design.md`, Phases 0, 2, and 3a.
- **Do not push a `vX.Y.Z` release tag between finishing this plan and Phase 3b's flip.** Task 3 removes the workflow that mirrors releases to the actually-public `strvmarv/zoid-releases`, but `create-release = true` still creates a release on whichever repo CI runs against — which is still the private repo until Phase 3b happens. A tag pushed in that window produces a release no real user can see (self-updater and public download links still resolve against `zoid-releases`, which gets nothing), with no error to flag it. See Task 3's caution note for detail.

```markdown
# AGENTS.md

Guidance for AI agents (and humans) working in this repository. Read this

## Release notes

`CHANGELOG.md` (root) is the single changelog — customer-facing and
developer-facing content live together in one file. Each version's `## X.Y.Z`
section must be a bare header matching the tag (e.g. `## 0.2.0` for tag
`v0.2.0`), or cargo-dist won't find a section to publish as that release's
announcement notes. Write the narrative and the engineering detail together;
dist appends the install one-liners and download table automatically.

## Cutting a release (summary)

Full runbook: **`docs/RELEASING.md`**. In short:

1. Bump `[workspace.package].version` in the root `Cargo.toml` (workspace-
   inherited; `zoid-testkit` is intentionally pinned and excluded).
2. Add a `## X.Y.Z` section to the top of **`CHANGELOG.md`**.
3. Regenerate the TUI snapshots — the status bar renders the version, so a
   bump changes ~35 insta frame snapshots. Run
   `cargo insta test --accept -p zoid-tui` and confirm `git diff` is
   **version-token-only** before committing them.
4. Verify the release gate: `cargo nextest run --workspace --features zoid/local-embed --no-fail-fast`

   (no piped-exit-code hazard) and parallelizes at the test level across all
   binaries. Use `--no-fail-fast` so one failing test doesn't hide others.
   `cargo test --workspace --no-fail-fast` still works as a fallback.
5. Commit, then `git tag vX.Y.Z && git push origin main --tags`. The tag push

It is generated by `dist generate` from `dist-workspace.toml`. Re-run
`dist generate` after any `dist-workspace.toml` change.

The TUI enforces a hard minimum of **160×40** (`layout::MIN_WIDTH` /
`MIN_HEIGHT`). Below this, a "too small" overlay renders instead of the normal
shell — `render_shell` and its sub-functions (`render_status`, `render_title`,
etc.) never run. This means renderers can assume at least 160 columns: no
narrow-terminal fallback, degradation, or progressive-collapse logic is needed
in render code.

## Memory

The maintainer (strvmarv) uses the **total-recall** MCP as the system of
record for decisions/corrections/preferences. Persist durable facts there;
do not hand-write into host memory files.
```

```markdown
# Releasing zoid

Users install prebuilt binaries via the installer script or `zoid update`
(anonymous, checksum-verified). No tokens live on user machines.

## How a release is wired

- `dist-workspace.toml` sets `create-release = true`: cargo-dist's `host` job
  creates the GitHub Release directly on this repo and uploads the build
  artifacts to it.
- `.github/workflows/release.yml` (generated by `dist generate` — do not hand
  edit; re-run `dist generate` after any `dist-workspace.toml` change) fires
  on `v*` tag pushes, builds the three targets, and uploads the archives,
  checksums, and installer scripts to the Release.
- Release notes come from cargo-dist's own changelog parsing: dist looks for
  a bare `## <version>` section in the root `CHANGELOG.md` matching the tag
  and uses it as the release's announcement body, appending its own install
  one-liners and download table.

## Cut a release

1. Bump the version: edit `[workspace.package] version` in the root
   `Cargo.toml`.
2. Add a `## X.Y.Z` section to the top of **`CHANGELOG.md`** (root)
   describing the release. The version header must be a bare `## X.Y.Z`
   matching the tag (e.g. `## 0.1.0` for tag `v0.1.0`) or dist won't find a
   section to use.
3. Regenerate TUI snapshots — the status bar renders the version, so the
   bump changes ~35 insta frame snapshots: `cargo insta test --accept -p
   zoid-tui`, then confirm `git diff` is version-token-only before staging
   them.
4. Commit: `git commit -am "release: vX.Y.Z"`.
5. Tag and push: `git tag vX.Y.Z && git push origin main --tags`.
6. CI (`release.yml`) cross-compiles the three targets and creates the
   Release with the archives, `sha256.sum`, per-archive `.sha256` files, and
   the `zoid-installer.sh` / `zoid-installer.ps1` installer scripts attached.
7. Verify: the repo's Releases page shows the release with all expected
   assets, and the published notes read correctly (from `CHANGELOG.md`).
8. Smoke-test: on a machine with an older zoid, run `zoid update`.

## First-time install (new machine)

Use the installer script from the latest release (`zoid-installer.sh` on
unix, `zoid-installer.ps1` on Windows). Afterwards, `zoid update` handles
upgrades.

## Push any `v*` tag

Tag pushes are what fire `release.yml` — no subagent should ever push a tag.
```

```markdown
# Security Policy

## Reporting a vulnerability

Please **do not** open a public GitHub issue for security vulnerabilities.

Instead, use GitHub's private vulnerability reporting: go to this
repository's **Security** tab and select **"Report a vulnerability"**. This
opens a private disclosure channel visible only to the maintainer until a
fix is ready.

If you're unable to use that flow, open a regular GitHub issue asking for an
alternative contact — without any vulnerability details in the issue itself.

## Scope

zoid executes tools on your behalf and communicates with LLM providers you
configure. Reports of particular interest include:

- Ways a crafted repository, file, or tool response could cause zoid to
  execute unintended commands.
- Credential or API-key handling issues (e.g. keys leaking into logs, config
  files, or provider requests they shouldn't reach).
- Anything that lets a plugin or MCP server escape its intended sandboxing.

## Response

This is a small, actively maintained project. Expect an initial response
within a few days; timelines for a fix depend on severity and complexity.
```
