# Spec 2 — Community Plugin Catalog (design)

**Status:** approved design, pre-plan
**Date:** 2026-07-13
**Depends on:** Spec 1 (Claude-Plugin Importer), merged to `main` (`947d142`)

## Goal

Let zoid users discover and install curated, community-contributed plugins from a
public catalog, without the plugins being compiled into the binary. Curated
manifests are hosted in the **public `strvmarv/zoid-releases`** repo (anyone can
contribute via PR); the zoid app fetches them **unauthenticated** via
`raw.githubusercontent.com` and surfaces them in a `:plugin` browse overlay with a
provenance-confirm gate before install.

## Non-goals (deferred to Spec 3 / later)

- **MCP catalog entries** (Spec 2.5). An MCP server is not a repo tree, so it does not fit
  the manifest→tree→materialize pipeline this spec reuses. Cataloging MCP servers needs its
  own manifest shape (an inline stdio `command`/`args`/`env` server table), a distinct
  install path that merges a server block into the user's `.mcp.json` (additive, stdio-only,
  with dedup), and a confirm step that shows the exact command to be run. Deferred to keep
  Spec 2 focused; **Spec 2 catalog kinds are `mode` and `skills` only.**
- Per-skill selective install + context-bloat guard (mega-catalogs).
- HTTP MCP transport (zoid MCP stays stdio-only; http servers are skipped+reported).
- Live in-session `app.skills` hot-reload (skills still load at startup; install
  reports a restart hint — see Spec 1).
- Overlay search/filter (the curated catalog is small, ~10-30 entries).
- Version-pinned catalog ref (the app reads the catalog off `main`).

## Background: what already exists (Spec 1)

The runtime install pipeline today (`crates/zoid/src/main.rs`):

1. `install_plugin(app, arg)` — `resolve_source(id, bundled_ids())` resolves an id to
   a `ManifestSource`. Today only `Bundled` is supported; `bundled_manifest(id)` returns
   a compiled-in `PluginManifest` (only `superpowers`).
2. The manifest's `[source] { repo, ref, subtree }` is turned into a GitHub URL and the
   **upstream skill tree** is fetched off-thread via `zoid::github_fetch::fetch_tree`
   (uses `api.github.com` git/trees for the listing — `$GITHUB_TOKEN` optional for rate
   limit — and `raw.githubusercontent.com` for blob contents), assembling an `UpstreamScan`.
3. The scan is handed back via `AgentUpdate::PluginScan { id, origin, over, res }`.
4. `apply_plugin_scan` re-resolves the manifest via `bundled_manifest(id)`, builds the
   plan, materializes the mode (or per-pack skills dir), applies Safe effects, reports status.

Spec 2 changes **only the manifest-resolution stage** (step 1/4) and **adds discovery**.
Steps 2–3 (upstream-tree fetch) and the materialize/effect machinery are reused unchanged.

## Architecture

Three parts:

- **(A) Catalog in `zoid-releases`** — a generated `index.json` (browse metadata) plus
  one full `<id>.toml` manifest per plugin, regenerated by CI.
- **(B) App `catalog` module** — fetch + TTL-cache + parse the index; resolve `<id>.toml`
  on install.
- **(C) `:plugin` overlay + `:plugin list`** — browse, show provenance, confirm, install
  through the existing pipeline.

### A. `zoid-releases` layout (public repo)

```
plugins/
  index.json          # GENERATED — the browse catalog (do not hand-edit)
  <id>.toml           # one full manifest per plugin (Spec 1 schema=1 format)
  README.md           # contributor guide
scripts/
  gen_index.py        # regenerates index.json from plugins/*.toml (stdlib tomllib; no Rust)
.github/workflows/
  catalog-index.yml   # on push touching plugins/*.toml: run gen_index.py, commit index.json if changed
```

`index.json` schema (`schema = 1`):

```json
{
  "schema": 1,
  "plugins": [
    {
      "id": "ok-skills",
      "name": "OK Skills",
      "kind": ["skills"],                    // "mode" | "skills" (MCP deferred to Spec 2.5)
      "description": "Curated skill pack.",
      "license": "MIT",
      "source": { "repo": "mxyhi/ok-skills", "ref": "a1b2c3d4e5f6...(40-char sha)" }
    }
  ]
}
```

- Each `index.json` entry is **derived** from the corresponding `<id>.toml`'s `[plugin]`
  (`id`, `name`, `kind`, `description`) and `[source]` (`repo`, `ref`); `license` is an
  optional field read from `[plugin].license` if present (else omitted).
- `gen_index.py` reads every `plugins/*.toml` with `tomllib`, emits `index.json` sorted by
  `id`, deterministic (stable key order, trailing newline). A generated index **cannot drift**
  from the manifests. The CI workflow regenerates and commits it so contributors never
  hand-edit `index.json`.

Contributor flow (documented in `plugins/README.md`): run the Spec 1 converter
(`zoid-plugin-import`) against a Claude plugin → commit the produced `<id>.toml` →
open a PR → maintainer review → CI regenerates `index.json` on merge.

### B. App `catalog` module — `crates/zoid/src/catalog.rs` (new)

Types:

```rust
pub struct CatalogEntry {
    pub id: String,
    pub name: String,
    pub kind: Vec<String>,          // ["mode"] | ["skills"] | ["mcp"] | ...
    pub description: String,
    pub license: Option<String>,
    pub source_repo: String,        // "mxyhi/ok-skills"
    pub source_ref: String,         // 40-char sha
}
```

- **Pure parse:** `parse_index(json: &str) -> anyhow::Result<Vec<CatalogEntry>>` — validates
  `schema == 1`, maps entries, unit-testable with no network.
- **Fetch + cache:** `fetch_catalog(now, ttl) -> anyhow::Result<Vec<CatalogEntry>>`:
  - Cache path: `resolve_cache_dir(env).join("catalog/index.json")` + a sibling
    `index.json.fetched` timestamp file (RFC3339).
  - If the cache exists and is younger than `ttl` (24h): parse and return it (no network).
  - Else fetch `https://raw.githubusercontent.com/strvmarv/zoid-releases/main/plugins/index.json`,
    write cache + timestamp, parse, return.
  - On network failure with a stale cache present: return the **stale cache** (degraded, not fatal).
  - On network failure with **no** cache: return an error the overlay renders as
    "catalog unavailable (offline)".
  - The clock (`now`) and env are injected for deterministic TTL tests (mirrors
    `resolve_config_dir`/`resolve_cache_dir`).
- **Resolve one manifest:** `catalog_manifest_url(id) -> String` (pure), returning
  `https://raw.githubusercontent.com/strvmarv/zoid-releases/main/plugins/<id>.toml`.

### C. Resolution seam — `install_plugin` / `apply_plugin_scan`

Extend id resolution:

- **Bundled first** (fast path, stays compiled-in for Superpowers): if `bundled_manifest(id)`
  is `Some`, use it, `origin = "bundled"`.
- **Else catalog:** fetch `catalog_manifest_url(id)` (raw, unauthenticated), `parse_manifest`
  + `validate`. `origin = "catalog"`. On 404/parse-fail: clear status error, write nothing.

The **resolved manifest is carried through the pipeline** rather than re-looked-up. Concretely,
`AgentUpdate::PluginScan` (and the in-flight install state) carry the resolved
`PluginManifest` (or enough of it), and `apply_plugin_scan` uses the carried manifest
instead of calling `bundled_manifest(id)`. This is the one structural change to the Spec 1
pipeline and is required for any non-bundled manifest to install. `--mode`/`--skills`
overrides continue to apply to the carried manifest exactly as today.

The upstream-tree fetch (`github_fetch::fetch_tree` over the manifest's `[source]`) and all
materialize/effect/status logic are unchanged.

### D. Surfacing UX

**Overlay** (`Overlay::PluginCatalog`, new variant, following `Overlay::Mcp` /
`Overlay::ProviderSwitch` conventions):

- `:plugin` (no args) opens it. On open, `fetch_catalog(now, 24h)` populates the list; a
  loading state shows while a fetch is in flight, an error state on offline+no-cache.
- Render each entry: `name` · kind badge (`[mode]`/`[skills]`) · `description`.
  `↑`/`↓` move the cursor.
- `Enter` → **confirm sub-state** showing provenance:
  `source: mxyhi/ok-skills @ a1b2c3d`, kind, and `license` if present, with
  `Install this pack? [y/N]`.
- `y` → run the install path for that id (same code as `:plugin install <id>`), close the
  overlay, status hint shows install progress/result. `n`/`Esc` → back to the list.

**Text command** `:plugin list` — prints the cached/fetched catalog (one line per entry:
`id  [kind]  description`). Non-interactive; also the no-TTY / scripting surface and an
easy integration-test path. Parsed in `crates/zoid-tui/src/command.rs` alongside
`plugin install`.

### Trust & safety

- Every catalog entry is a **maintainer-reviewed PR** to the public repo — that review is the
  human trust gate.
- Manifests carry **pinned 40-char SHAs**; an install fetches exactly that pinned tree, so
  it is reproducible and auditable.
- The overlay and the confirm step always display **source repo@sha + kind + license** before
  anything is written to disk.
- No new execution surface: installs go through the Spec 1 mode/skills pipeline whose v1 gate
  already rejects all `SetConfig` and Dangerous effects before touching the filesystem.
  (MCP-server catalog installs — which would run a command — are out of scope here; see Spec 2.5.)
- Secrets: the catalog fetch is unauthenticated (public repo); the upstream-tree fetch uses
  the optional `$GITHUB_TOKEN` exactly as today and never logs it.

### Error handling

| Situation | Behavior |
|---|---|
| Offline, no cache | Overlay: "catalog unavailable (offline)"; `:plugin list` prints the same. |
| Offline, stale cache present | Use stale cache; note "(cached)" / last-updated in the overlay footer. |
| Malformed `index.json` | Error; keep the prior valid cache if present (do not overwrite it with garbage). |
| `:plugin install <unknown-id>` | "plugin '<id>' not found in catalog" (after bundled miss + catalog miss). |
| `<id>.toml` 404 or parse/validate fail | Clear status error; nothing materialized. |
| Network failure during upstream-tree fetch | Existing `PluginScan` error path (unchanged). |

### Testing

- **Pure `parse_index`:** valid index; wrong `schema`; missing required field; unknown kind
  string preserved (validation of installability happens later via `validate`).
- **TTL cache logic:** fresh cache → no fetch; stale cache → refetch; network-fail-with-stale
  → returns stale; network-fail-no-cache → error. Clock + fs injected; no real network.
- **Resolution fallthrough:** bundled id → bundled manifest; non-bundled id → catalog URL
  resolution; unknown id → error. (Manifest carried through, not re-looked-up.)
- **Overlay state machine:** open → list; `Enter` → confirm; confirm `n` → list; confirm `y`
  → triggers install for the selected id. Confirm gate **blocks** install until `y`.
- **`:plugin list` parse** in `command.rs`.
- **Fixtures:** a sample `index.json` and a sample `<id>.toml` under the crate's test fixtures.
- Network fetch itself is not unit-tested (mirrors `github_fetch`); an integration smoke test
  may hit the real catalog once if desired.
- **`gen_index.py`:** a small self-check (round-trip a fixture `plugins/` dir → expected
  `index.json`), runnable in the `zoid-releases` CI.
