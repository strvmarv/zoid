# Releasing zoid

Source is private (`strvmarv/zoid`); binaries are published to the public
`strvmarv/zoid-releases`. Users self-update with `zoid update` (anonymous,
checksum-verified). No tokens live on user machines.

## One-time setup (maintainer, not automated — see "Maintainer steps" below)

- Public repo `strvmarv/zoid-releases` created.
- Fine-grained PAT (Contents: Read and write, scoped to `zoid-releases` only)
  stored as the `RELEASES_REPO_TOKEN` secret in the private `strvmarv/zoid`
  repo's Actions secrets.

## How a release is wired

- `dist-workspace.toml` sets `create-release = false` (no Release object is
  meant to be the source of truth in the private repo) and
  `publish-jobs = ["./publish-public"]`.
- `.github/workflows/release.yml` (generated by `dist generate` — do not hand
  edit; re-run `dist generate` after any `dist-workspace.toml` change) fires on
  `v*` tag pushes, builds the three targets, and after its `host` stage runs a
  `custom-publish-public` job that calls the reusable workflow
  `.github/workflows/publish-public.yml`.
- `publish-public.yml` downloads the build's archives/checksums/installers
  (uploaded earlier in the same workflow run under the `artifacts-*`
  `actions/upload-artifact` names — the same pattern the generated `host` job
  uses) and runs `gh release create` against `strvmarv/zoid-releases`,
  authenticated with `RELEASES_REPO_TOKEN` (not the default `GITHUB_TOKEN`,
  which only has rights in the private repo).

## Cut a release

1. Bump the version: edit `[workspace.package] version` in the root `Cargo.toml`.
2. Write release notes in `NOTES.md` by hand. Do NOT paste the private commit
   log — this file becomes public (it is uploaded/read from the checkout in
   `publish-public.yml`).
3. Commit: `git commit -am "release: vX.Y.Z"`.
4. Tag and push: `git tag vX.Y.Z && git push origin main --tags`.
5. CI (`release.yml`) cross-compiles the three targets and the `publish-public`
   job creates the Release at `strvmarv/zoid-releases`.
6. Verify: the public repo's Releases page shows three archives + `sha256.sum`
   (plus per-archive `.sha256` files and the `zoid-installer.sh` /
   `zoid-installer.ps1` installer scripts).
7. Smoke-test: on a machine with an older zoid, run `zoid update`.

## First-time install (new machine)

Use the installer from the latest release on `strvmarv/zoid-releases`
(`zoid-installer.sh` on unix, `zoid-installer.ps1` on Windows). Afterwards,
`zoid update` handles upgrades.

## Token rotation

`RELEASES_REPO_TOKEN` (fine-grained PAT, Contents: Read and write on
`zoid-releases` only) lives in the private repo's Actions secrets. On expiry
the `publish-public` job fails loudly (the `gh release create` call in
`publish-public.yml` errors out); regenerate the PAT and:
`gh secret set RELEASES_REPO_TOKEN --repo strvmarv/zoid --body "<PAT>"`.

## Maintainer steps not automated by CI

These require the maintainer's own `gh` auth / GitHub credentials and are not
run by any subagent or CI job:

1. **Create the public repo** (one-time):
   ```bash
   gh repo create strvmarv/zoid-releases --public \
     --description "Prebuilt zoid binaries (source lives in the private strvmarv/zoid)."
   ```
   Add a short `README.md` to it explaining it is the distribution point only
   (no source).
2. **Create the fine-grained PAT** (one-time, and again on rotation): scoped
   to `strvmarv/zoid-releases` only, permission Contents: Read and write.
3. **Store the PAT as a secret** (one-time, and again on rotation):
   ```bash
   gh secret set RELEASES_REPO_TOKEN --repo strvmarv/zoid --body "<the-fine-grained-PAT>"
   ```
4. **Push the smoke tag** to prove the end-to-end pipeline before a real
   release:
   ```bash
   git tag v0.0.1-test && git push origin v0.0.1-test
   ```
   Confirm: `release.yml` runs green; `publish-public` creates a
   `v0.0.1-test` release on `strvmarv/zoid-releases` with the three archives +
   `sha256.sum`. Then, from a build of this branch, `zoid update` (matching
   `ZOID_TARGET`) upgrades to it.
5. **Clean up the smoke release and cut the real one**:
   ```bash
   gh release delete v0.0.1-test --repo strvmarv/zoid-releases --yes
   git push --delete origin v0.0.1-test
   git tag v0.1.0 && git push origin v0.1.0
   ```
   Confirm: the real `v0.1.0` release appears on the public repo; `zoid
   update` on an older binary upgrades to `0.1.0`.
6. **Push any `v*` tag** in general — tag pushes are what fire `release.yml`;
   no subagent should ever push a tag.
